## Scope and source evidence

`paired-contact-manifest/v1` pins an immutable source manifestId/manifestRevision/hash and one registration, business/account/origin/runtime, exact case/order/TWO distinct existing customer UUIDs with case/order/customer/contact/material revisions, independently enrolled native executor/source principal, purchaser statement text/hash, and ordered email+SMS channels. Null identity/contact/material fields cannot produce a manifest. The 121399 and 121007 preparation packets are separate; nothing fills 121007's missing fields from 121399.

Each channel pins source account, from, sole recipient, subject, attachments' names/hashes, rendering revision, and public segments with exactly one matching source-generated single-use link slot. Slot policy: independent 256-bit secret, base64url, exact HTTPS origin/path, fragment only, binding to authority/generation/channel/intent. No arbitrary substitutions, footer or normalization. SMS is exact E164, empty subject/no media. Template hash commits all channel fields except templateHash. Native never receives/stores the actual secret or secret-bearing URL, nor recomputes final secret wire bytes. Source must have independently accepted renderer/dispatch and secure redemption implementations and prove actual mediated wire hash at the provider boundary; bot-supplied hashes are never evidence.

Dedicated authenticated source GETs, empty query/no redirects/fallback:
- `/api/cs/contact-verification/native/manifests/:registrationId` returns paired-contact-evidence/v1.
- `/api/cs/contact-verification/native/intents/:intentId` returns contact-dispatch-evidence/v1.

Both use a genuinely dedicated native-owned use-time reader credential, not Nora's credential or another integration grant. Evidence binds registration ID/hash and service principal. Case-manifest evidence also commits source revision, complete coverage/omissions/blockers and full manifest. Observations last at most15 seconds and do not extend durable expiry. The source owner must explicitly accept these producer routes and DTOs before implementing or enabling their adapter; publication of this native candidate is not source acceptance. Source must independently authenticate all IDs and enrollment, not reflect requested bot data.

## Paired generation and association

One immutable preparedEventId audits atomic creation of the generation and BOTH intent cores, not invented separate audit events. Before native redemption or provider calls, source transaction commits ONE generation and BOTH channel intents with distinct IDs, keys, provider idempotency keys and independent slot commitments. `paired-contact-generation/v1` commits authority/registration/business/manifest/executor/source/material, prepared event/time, original capped expiry and ordered email/SMS intent cores. Each intent has template, slot commitment, final wire payload hash and provider key. Source owns safe secret custody and wire rendering. Actual final wire must still match immediately before its sole provider request.

Source durably CASes selected channel to REDEEMING, with distinct durable event/time after generation prepare, before POST `/api/contact-verification/verifier/dispatch-associations`. Strict request is contact-dispatch-association/v1. Native independently reads exact persisted source intent, complete paired generation and fresh manifest, then atomically rechecks approval/context/trust/revocation, consumes permanent generation/channel reservation and persists authenticated bindings. First response only dispatchEntitlement:true and execute:false. No bot claim surface. Source readback includes required nullable sendingEventId/sendingAt: null in REDEEMING; genuine distinct event/time after redemption and before original expiry in SENDING/SENT_ACCEPTED. UNKNOWN/terminal rollback may have null when no SENDING commit exists; never retry. Source persists SENDING before provider, caps at authority expiry and applies current actor/material/lease/assignment/opt-out/local-hours/account/capacity guards. Native does not prove those checks merely from a schema or acceptance hash.

One immutable generation per authority; one dispatch reservation per specified channel. Permanent authority, intent, request-key and provider-key uniqueness survives revocation/expiry/UNKNOWN and terminal rollback. Source preserves its own unique issuer/business/authority/generation/channel and all original action records. A new native decision/key/registration with the same exact case/order/two-customer target cannot escape the native permanent target fence. No automatic resend/new generation.

Email must reserve first; SMS requires that exact email association and its authenticated SENT_ACCEPTED receipt. Required nullable pairBlock on source intent evidence is {eventId,at,reason:UNKNOWN|ROLLED_BACK_TERMINAL,intentId}. Source persists the first pairBlock independently and immutably on UNKNOWN or rollback, projects it for BOTH intents forever, and never clears it after later reconciliation. Native persists an immutable pair-block audit even when first observed through an unstarted channel before any native association; it also permanently blocks from ANY immutable UNKNOWN/rollback receipt. Neither path depends merely on the latest outcome. Changing or clearing the first observed block denies. A later email SENT_ACCEPTED reconciles history but NEVER releases blocked SMS. SENDING/absent outcome blocks SMS pending reconciliation. This intentionally conservative sequencing is not all-or-nothing delivery. Source must reconcile first accepted outcome before starting sibling. Replayed first response or GET never grants entitlement again. Concurrent revoke-before-association denies; association-before-revoke reservation is irreversible, no distributed cancellation promise. Source never retries after losing an entitlement response, even if local rollback proves no effect.

GET `/api/contact-verification/verifier/dispatch-associations/:associationId` is exact authenticated read-only reconciliation (false entitlement). POST `/api/contact-verification/verifier/receipts/:associationId` accepts only empty body and reads original authenticated source intent. Lost association IDs reconcile through POST `/api/contact-verification/verifier/dispatch-associations/lookup` with the entire unchanged original strict contact-dispatch-association/v1 request. It authenticates current registration and original immutable authority, compares the full stored request digest and returns {execute:false,dispatchEntitlement:false,retryAllowed:false,association:existing|null}. An occupied authority/channel or any permanent unique intent/request/provider/digest key with a different binding returns conflict, not absence. Absence is not permission to retry; it neither fetches source nor reserves. No replay of association POST is required. Outcome commits exact association/generation/intent through the envelope, provider account/key/wire hash, provider ID for SENT_ACCEPTED, audit event/time, noRetry:true. UNKNOWN may have null association/provider IDs after a lost response. Terminal outcomes require actual association; rollback provider ID is null. Native permits UNKNOWN to settle once; conflicting terminal proof denies. Accepted is provider acceptance, not delivered, purchaser identity, source association or financial clearance.

## Canonical hashes and trust

C = recursive ordinal-key-sorted UTF8 JSON, explicit nulls, array order, unchanged strings. H(domain,value)=SHA256(C({domain,value})). Domains: contact-verification/template/v1, statement/v1, manifest/v1, evidence/v1, authority/v1, intent/v1, generation/v1, dispatch-evidence/v1, outcome/v1. Self hash excluded; evidence additionally excludes only observedAt/expiresAt. Intent preimage is explicitly selected in intentDigest: generation/authority/hash/registration/hash/business/manifest/source/material/executor plus channel core excluding intentHash. Provider key and request key remain committed. Native internal inspection/context/enrollment hashes are separate native-only domains. Source-only slot commitment is H(`contact-verification/slot/v1`, {authorityId,generationId,intentId,channel,slotId,secret}); secret is exactly 32 independently random bytes encoded as unpadded base64url. It is never included in native evidence. Source must decode and round-trip the canonical unpadded base64url representation to exactly32 bytes, not accept a length-only secret check. Source-only wire hash is H(`contact-verification/wire/v1`, {authorityId,generationId,intentId,channel,accountId,from,recipient,subject,body,attachments}), using exact final UTF8 strings and ordered approved attachment hashes, with the sole slot rendered as origin+path+'#'+generationId+'.'+channel+'.'+secret. The slot pins fragmentEncoding='generation-channel-secret/v1': canonical lowercase generation UUID, literal email or sms, and exactly43 unpadded base64url secret characters separated by periods. All three fields remain in the fragment; source parses them only for explicit POST and checks the durable generation/channel/intent. No Unicode/body/footer/URL transformations are allowed after commitment. Native golden vectors treat these two source-only hashes as opaque synthetic commitments, not evidence that native inspected secret bytes. Source must supply independent renderer/boundary tests before acceptance.

Service auth: X-Contact-Registration-Id + dedicated bearer + CF service JWT audience/common_name. No arbitrary audience header/human JWT or trust reuse. Registration hash is canonicalSha256(entire strict registration). New optional VP_CONTACT_VERIFICATION_REGISTRY_FILE is absolute regular non-symlink service-owned0600 <=128KiB. No registry or credential is created here. Missing/invalid trust yields CONTACT_VERIFICATION_UNAVAILABLE; malformed contract400; stale/mismatched/unapproved/revoked/ambiguous/UNKNOWN or duplicate conflict409; wrong actor403. Read-only reconciliation requires current dedicated identity but does not revive old authority.
