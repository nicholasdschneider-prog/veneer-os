# Native QBO phase and invocation contract v2 — staged for review

October 13, 2026. Platform owns native code; Boris owns canonical helper adaptation; Clara owns accounting acceptance. No production adapter, grant mapping, enrollment, refresh or accounting acceptance is installed. This contract does not change v1 receipt meaning or synthesize phase proof from v1 history.

## Exact native interface

Authenticated POST `/api/bots/qbo/v2/invoke` takes strict `{request:qbo-operation/v2,bytes:{payloadBase64,attachmentsBase64}}`. The original native per-turn session is resolved server-side exactly as in v1. No supplied user identity, command, environment, executable, source receipt or provider outcome is accepted. Original payload bytes and ordered PDF bytes are checked against the independently authorized operation, held in memory and passed on private stdin; never retained in the ledger. Decoded payload limit 1.5 MiB (2 MiB base64 input), PDF limit 25 MiB, one PDF, total route bound 40 MiB. No native token or credential enters the helper frames.

POST `/v2/read` and `/v2/reconcile` take `{requestKey}`. Read is native durable history only. Reconcile invokes the same pinned helper in **receipt-only** mode after independent current custody and original-caller verification by a server-owned reconciliation adapter. No credential/refresh/provider call is permitted by this mode. No source receipt import endpoint exists. Production resolvers and transport are unavailable by default. Strict schema source is `server/src/qbo/phaseContract.ts`.

`qbo-operation/v2` retains exact independent assignment/accounting authority, current grant/company, original executor and source context. New operation kinds: read-bill, create-bill, update-bill, attach-pdf, verify-attachment. Provider method/path, exact payload and attachment bytes, original request key and company commit to H(qbo/provider-request/v2,...). One dispatch acknowledgment covers **one** specified provider request, no hidden reads, redirects or automatic retry. Query-like verify-attachment is a bounded GET `/query`; it is NOT the existing full download/content-verification workflow. A multi-request verification requires further accepted protocol scope; do not label one query as full verification. Existing helper's implicit Bill reads/upload/verifier subrequests must be accounted for before source acceptance.

V2 uses the same permanent qbo/logical-effect/v1 identity and reservation table as v1. Version/key/assignment changes never free an effect. V1 admission additionally honors unresolved v2 grant fences. This is native defense only; all source grant consumers must honor the same fence before integration can be accepted.

## Authenticated local transport

Native uses the existing child-process/private-pipe mechanism, not a new network service, OAuth grant or shared bearer. The server-owned facts adapter returns an accepted descriptor containing runtime kind, canonical absolute interpreter/script/dependency paths and SHA256s, UID, dependency-closure review hash and acceptance hash. The entire descriptor is committed by qbo/helper-process/v1 and matched against independent integration evidence. Bots cannot install descriptors.

The adapter rejects symlinks, wrong UID, group/world writable or nonregular/oversize files, hashes opened bytes, then freezes the executable and source dependencies into a private temporary directory. It executes those copied bytes with no shell, controlled cwd, only LANG/TZ environment, private stdin/stdout and discarded stderr. Python uses `-I -S -B`; Node uses `--no-addons`. No application environment, native token, startup options, caller-selected arguments or extra descriptors are inherited. Source runtime/module import closure and dynamic-library dependencies still require exact acceptance; a hash list is not OS sandboxing or proof against another process with the same OS UID. A runtime that cannot execute from the frozen layout fails closed (for example a relative-library Homebrew interpreter). No fallback to the unpinned original is allowed. Python helper adaptation must explicitly load only accepted frozen sibling modules under isolated mode. No source runtime compatibility is claimed from the synthetic helper.

Transport sends one newline-framed `qbo-invocation/v2` containing reservation, request, bytes and native initial phase. Child must hold canonical qbo.lock and validate held bytes before asking refresh-start. Frames are bounded to 32 KiB, at most 100 events, 30-second process deadline. No raw child diagnostics are retained. Native records each permitted STARTED phase **before** acknowledgment. Native transport errors terminate only its child, never another service; durable uncertainty remains. Parent failure leaves an open durable phase and fences the grant. Source must maintain its own write-before-call audit, survive lost acknowledgments without replay and persist rotated tokens regardless of later authorization expiry. Native alone cannot guarantee source behavior.

## Phase protocol

Strict helper event: schemaVersion qbo-helper-event/v2, invocationId, receiptId, sequence, previousHash, action, evidenceHash, providerRequestHash|null, billResult|null. Sequence and previousHash bind the complete previous receipt's reservation/job/effect/scope/payload. Native appends immutable qbo-phase/v2 including these fields, actual native recordedAt and refresh/persistence/dispatch states. No tokens, fingerprints, URLs or raw errors are permitted in evidence.

Initial sequence0 is explicit native write-before-command evidence: refresh not-started, persistence not-applicable **only because refresh has not been permitted**, dispatch not-started. An empty ledger never supplies this proof. `refresh-start` commits started + persistence uncertain, then alone returns refreshEntitlement true. `refresh-confirmed` requires started and authenticated exact source response evidence. `persistence-confirmed` requires confirmed refresh and durable canonical rotated-token persistence evidence; it may be recorded after session expiry/revocation, but grants nothing. `persistence-uncertain` closes and fences the grant. Confirmed persistence cannot regress.

`dispatch-start` requires confirmed refresh/persistence plus fresh original caller, assignment, independent accounting scope, exact facts, original admission expiry and current observation. It commits STARTED before its sole operationEntitlement acknowledgment. Accepted/UNKNOWN dispatch must match the exact provider request hash. `stop` or transport loss conservatively retains uncertainty for any STARTED phase. No renewed request key or rollback retry exists. Unresolved persistence/open invocation blocks all native same-grant admissions, including distinct effects.

Reconciliation can only advance authenticated historical UNKNOWN to confirmed refresh/persistence or accepted dispatch; it cannot emit either STARTED permission. Strict exact receipt-ID/hash replay returns historical acknowledgment with all entitlements false, including after terminal evidence. Changed same ID conflicts. New terminal regressions or changed terminal evidence conflict. Read never grants entitlement. Expired authority does not prevent necessary token persistence evidence from the already-owned process; new dispatch still fails. Old v1 SUCCESS is not v2 phase evidence.

## Independent Bill observation

read-bill uses exact Bill ID and company without a fabricated SyncToken. It requires its own independently authorized logical effect, admission, same grant/lock and refresh. Accepted authenticated result stores an immutable content-addressed native observation bound to read reservation, original executor, business/grant/company/Bill, observed SyncToken, source revision, result digest and actual source capturedAt. Expiry is min(capturedAt+15s, original read admission expiry); reconciliation never stamps old evidence with a new capture time.

A later operation references the stored observation hash, not caller-supplied result. Native checks exact identity, original executor/source revision and expiry both at reservation and dispatch. Update-bill additionally requires exact observed SyncToken; its payload still needs independent exact accounting permission. Attach/verify use observation as identity/freshness evidence and send no fictitious SyncToken CAS. Source current material, human assignment, canonical readiness and actual provider semantics remain mandatory. Observation is neither write authority nor a reservation for later work.
