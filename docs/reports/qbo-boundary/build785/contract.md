## Normative schema, timing and entitlement meaning

Normative strict parser: [server/src/qbo/contract.ts](/Users/archerclawdington/veneer-os/server/src/qbo/contract.ts), with byte commitments in [schema-manifest.json](./schema-manifest.json). H is native canonicalSha256({domain,value}), recursively ordinal-key-sorted compact UTF-8 JSON; arrays ordered, null preserved. sourceContextHash uses qbo/source-context/v1 over the full typed sourceContext array. authorityScopeHash uses qbo/authority-scope/v1 over businessId/accountRef/existingGrantRef/companyRealm/executorConversationId/operation. Existing source identifiers and revisions are required; no inferred company/account/grant mapping.

`execute:false` means this native API performs no QBO operation and grants no generic bot execution. Only a FIRST online helper admission's paired refreshEntitlement:true/operationEntitlement:true may be consumed by the separately accepted canonical helper, once for this exact effect. Never treat a copied response or these flags in caller input as verification. With the current production unavailable adapter there is no positive admission at all.

The helper must reject an expired admission before refresh AND before provider dispatch. After refresh it must persist any rotated token through the existing runtime even if the admission has expired, then re-run online native inspect under the same original identity and compare factsHash/scopeHash to the original reservation, recheck the original expiresAt, existing qbo gate and source material. That inspection grants no new entitlement and cannot extend the reservation. Expiry/revocation/drift after refresh means no provider dispatch and permanent FAILED_NO_RETRY/UNKNOWN reconciliation, never another refresh/admission under a new key. Native first-admission lifetime is at most15seconds and capped by both facts and integration expiry. Source implementation must test slow refresh, token persistence and expiry before claiming enforcement; native tests cannot prove that source sequence.

Every response has a strict schema in the normative module (inspection, first admission, read, reconciliation, error). ABSENT means no matching native receipt was found, NOT no QBO effect or retry permission. RESERVED means permanent historical consumption, NOT queued/pending work. Read returns at most100 immutable receipts; larger histories fail closed explicitly. SUCCESS requires authenticated durable provider evidence (request correlation, response digest, entity ID when present) retained and revalidated by the source receipt adapter. A hash supplied by a bot is never sufficient. UNKNOWN may later reconcile to a proven terminal result without retry entitlement. Conflicting terminal status/evidence is rejected and prior receipts remain immutable; no-success rollback cannot later be relabeled success. No provider read is performed by this native receipt consumer.

The reservation is additionally capped at the actual native session expiry obtained server-side from agent_tokens. The receipt's FAILED_NO_RETRY is a proven terminal failure without a successful effect; unresolved provider effects MUST remain UNKNOWN. No terminal outcome may flip or regress to UNKNOWN, even under a different receipt ID. Changed terminal evidence is refused for separate accounting review. This does not weaken the permanent reservation.
